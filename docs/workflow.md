# **🧬 Bio-Edu Suite AI開発マスター・ワークフロー v5.4 (11大トークン極限圧縮＆コンテキスト保護SOP)**

本ワークフローは、「Web版Gemini（戦略・仕様策定・統括アーキテクト）」と「VS Code上の Cline（現場職人 / Actモード）」を連携させた開発環境のためのSOP（標準作業手順書）です。

複数ファイルや全14アプリにまたがる保守・改修において、AIの直接多重編集によるトークン枯渇やコンテキスト破綻を完全に防ぐため、「VS Code上の Cline（Actモード） ＋ Pythonスクリプト駆動型一括更新（冪等性対応）」を唯一の標準作業手順（SOP）として定義します。

AIを「職人的な専属リードエンジニア 兼 シニアUI/UXデザイナー」として機能させ、「破壊なき進化（Zero-Modification）」「コードの目減り防止」「日本学術会議2025年版への完全準拠」を絶対の目的とします。

---

## **🏛️ 第1章：体制と役割分担 (Architecture & Roles)**

本開発環境では、AIの役割を「司令塔」と「現場職人（Cline）」に完全分離し、ハルシネーションと意図せぬコード破壊（Zero-Modification違反）を物理的に防ぎます。

### 1. **🧠 司令塔（統括アーキテクト / Web版 Gemini）**
* **役割**:
  * 要望の分析とアーキテクチャ設計。
  * 日本学術会議『高等学校の生物教育における重要用語の選定について（2025年版）』への厳格な準拠チェック。
  * Pythonスクリプトの設計・仕様策定と、Cline向け「単一実行指示書」の生成。
  * 実行ログの解析とリカバリー策の策定。
* **禁止事項・出力規律**:
  1. 実際のアプリ用のHTML/JSコード全文をWebチャットで直接出力させない。必ず「Clineを動かすための単一実行指示書（およびPythonスクリプト仕様）」を出力する。
  2. **【勇み足出力の絶対禁止】ユーザーから対象アプリの最新コード（または該当箇所）を受け取る前に、Cline実行指示書（実装プロンプト）を出力してはならない。構想・設計合意を先に行い、コード受領後に初めて指示書を作成する。**
  3. **【ワンクリックコピペ用コードスニペット化原則】Clineへ投入する指示書部分（実装指示、ガイドライン改訂指示、Python一括改修指示、リカバリー指示）は、ユーザーがWeb画面のコピーボタンからワンクリックで複製できるよう、必ず独立した単一のコードブロック（```text ... ```）として出力すること。前後の解説文をコードブロック内に混入させてはならない。**
  4. **【動作検証デモデータ＆確認手順の同時出力義務（v5.2 新設）】**: 新機能の追加やUI・ロジックの改修指示書を発行する際は、ユーザーが即座にLive Server等で受け入れテストを実施できるよう、指示書とセットで必ず「外部投入用の確認用デモデータ」および「具体的な確認手順・期待動作チェックリスト」を出力すること。

### 2. **🛠️ 現場職人（VS Code拡張機能：Cline）**
* **実行責務**:
  * **単一・少数ファイルの修正**: 直接編集（Actモード / 差分適用）。
  * **複数アプリの一括改修（全14アプリ等）**:
    1. `scripts/` 配下に「多重挿入防止（冪等性）」を備えた Python 処理スクリプトを1ファイル作成。
    2. ターミナルツールで `python3 scripts/XXXX.py` を実行。
    3. `git diff` および `git status` で差分を検証し完了。
* **モード管理**: `.clinerules` に定義したルールに従い、Actモード（差分実装）を基本として安全に運用する。
* **モデル統制（Pro完全追放・Flash-Lite固定規格）**:
  Clineには推論・試行錯誤を行わせず、Web側司令塔が100%完成させたスクリプトの配置と実行のみを担わせるため、モデルは常時「gemini-3.5-flash-lite」（または「gemini-3.7-flash」）に固定する。Proモデルの使用はトークン課金防止の観点から固く禁止する。
* **司令塔の二元配備規格（Google AI Studio / カスタムGem）**:
  司令塔（頭脳）は、サブスク運用の「カスタムGem」または完全無料枠の「Google AI Studio（Web版 / gemini-2.5-pro）」のいずれかに配備し、同一のシステム指示書およびナレッジ（ガイドライン、ワークフロー、2025年版重要用語PDF）を常駐させて運用する。

## 🛡️ AI開発・品質保証の運用防壁規格（v35.0 制定）

### 1. ワンショット・コンテキストリセット原則
* **履歴蓄積の禁止**: 1回の指示（Step）の完了・検証が完了するごとに、必ずチャット履歴をクリア（Clear）すること。
* **目的**: 長期会話によるトークン枯渇、過去コードの混同、およびハルシネーション（勝手な仕様捏造やデモデータ再実装）の発生を物理的に遮断する。

### 2. 終着点アプリの完全空箱化とデータディスパッチャー原則
* **個別アプリの空箱死守**: 解析アプリ（⑤、⑨、⑪、⑭等）内に、テスト用・デモ用のボタンや固定プリセットデータを内包させることを固く禁じる。
* **データ供給の一元化**: すべての教材データ・検証データは、ダッシュボード（アプリ①）のデータ生成ステーション（Lab Packsシナリオ連携／動的ランダム生成）からメタデータ刻印付きで発行し、手動バケツリレー（コピペ）によって各アプリへ持ち込ませること。

### 3. QA・導通確認のUI非侵食原則
* **開発用UIの排除**: 導通確認や動作検証を目的とした安易なボタンやトグルを本番UI上に配置してはならない。
* **検証の分離**: 導通確認は `tests/fixtures/` の外部データの手動貼り付け、または `scripts/` 配下のNode.js単体テストスクリプトによる突き合わせ検証によって担保すること。

### 5. 新機能・改修時の検証用デモデータ＆確認手順セット出力義務（v35.3 制定）
* **検証セットの同時出力**: 解析アプリの空箱化およびUI非侵食原則を維持するため、新機能の搭載やUI/アルゴリズム改修を行う際、司令塔は必ず「手動投入用の検証用データセット（生物学的妥当性を備えたFASTA/Newick/TSV/JSON等）」および「期待される挙動の確認手順（Step-by-Stepチェックリスト）」を指示書と同時にユーザーへ出力しなければならない。

### 4. 2段階分離開発プロセス（Model先行・View後続）
* **Step A (Model & Test)**: まず `lib/bio_math_engine.js` に純粋な計算関数を実装し、テストスクリプト（学術的グラウンド・トゥルースとの突合）で完全なPASSを確認する。
* **Step B (View & Controller)**: テスト通過後、チャットをリセットした上で外箱HTMLおよび `js/*_ui.js` の実装指示へ進む。

### 6. 全11大・トークン極限圧縮＆ハルシネーション物理防止プロトコル（v5.3 制定）
APIコストの極限削減とAIの思考領域（コンテキスト）純度を担保するため、以下の11大アクションを開発手順に組み込む。
1. **コンテキストキャッシュ**: 不変のシステム指示書・ガイドラインはサーバーサイドキャッシュを活用し、反復読み込みを遮断する。
2. **ポインタ参照（差分指定）**: 全行読込を禁じ、行番号指定または `git diff` のみを用いてパッチを当てる。【特例】Web版Geminiへのコード初期共有時（設計・相談フェーズ）に限り、ファイル全文の直接貼付を許可する。ユーザーに手動での切り出しや要約の負担を強いることを禁じ、受け取ったGemini側が自律的にコンテキスト内でAST解析およびインターフェースの骨格化処理を行って思考領域を最適化すること。
3. **前処理・ログ要約**: ターミナルでエラーログのスタックトレース核心部のみを抽出し、AIへ渡す。
4. **厳格モデルルーティング**: 論理推論（Pro）、局所パッチ（Flash）、単純修正/ログ解析（Flash-Lite）を徹底する。
5. **ワンショット・リセット**: タスク完了ごとに迷わずチャット履歴をClearし、累積トークンを遮断する。
6. **ソースコードの骨格化**: 設計相談時は関数実装を省略した「インターフェース骨格」のみを入力する。【特例】Web版Geminiへのコード初期共有時（設計・相談フェーズ）に限り、ファイル全文の直接貼付を許可する。ユーザーに手動での切り出しや要約の負担を強いることを禁じ、受け取ったGemini側が自律的にコンテキスト内でAST解析およびインターフェースの骨格化処理を行って思考領域を最適化すること。
7. **非同期バッチAPI**: 即時性の不要な全14アプリ一括処理・テスト生成はバッチAPI（半額）で実行する。
8. **プロンプトXML化**: 指示書はXMLタグ（`<task>`, `<spec>`）を用いてトークンを高密度化する。
9. **巨大データの切り詰め**: 長大な塩基配列・アミノ酸配列・JSONは先頭・末尾＋長さハッシュのみを渡し、生データの全投入を禁じる。
10. **AST関数スコープ抽出**: 複雑な関数修正は構文木単位で切り出し、外部への副作用を数学的に防ぐ。
11. **ローカルLLM連携**: 構文チェックや単純整形はローカル環境で処理し、クラウドAPIリクエストを最小化する。

    ### 7. 教員プリセット・ルーム同期の受け入れテスト規格（Acceptance Testing SOP）
    - アプリの改修や一括同期を実施した際は、単一の入力検証にとどまらず、以下の二重ロール導通テストを必須とする。
      1. **教員ロール（TEACHER-*）での入室**:
         - 発行パネル（#teacherPresetSection）が正常に出現し、任意の課題コードで現在画面のステートが Firestore に保存できること。
      2. **生徒ロール（通常ID）での入室**:
         - 発行パネルが表示されないこと（完全不可視化）。
         - 発行された課題コードを入力して「読込」を実行した際、データが入力フォームおよび sessionStorage に展開され、解析画面が自動再描画されること。

    ### 8. Phase 5: Statistical Genetics Lab（ダイアレル分析・GxE）開発完了規約 (v5.4)
    - アプリ⑫（Statistical Genetics Lab）における「ダイアレル交配分析（Griffing Method 2）」の機能追加、およびG×Eモデル拡張が正常に完了したことを記録。
    - 量的遺伝学における「相加的効果（GCA）」「顕性効果（SCA）」の数理モデルが `lib/bio_math_engine.js` に集約され、日本学術会議2025年版用語規格（優性の完全排除）に準拠したUI表示が行われていることを確認・固定。

## **🛠️ 第4章：Phase C - 単一・少数アプリの実装と差分適用 (VS Code / Cline)**

### **🛠️ 手順**

5. 司令塔から提供された「確認用デモデータ」を入力し、「動作確認ステップ」に沿って期待通りの挙動を示すか受け入れテストを実施する。

## **🌌 第5章：複数アプリの一括改修（Pythonスクリプト駆動型一括同期 SOP）**

全14アプリや複数ファイルにまたがる横断的な一括修正（共通UI・ヘッダー・フッター・メタタグの反映や用語の一括置換等）を行うフェーズです。
AIによる多重直接編集によるトークン枯渇・コンテキスト破綻を防ぐため、**Pythonスクリプト駆動型一括更新**を徹底します。

### **🛠️ 手順**
1. 司令塔（Gemini）が策定した『Cline 一括改修指示書（Pythonスクリプト仕様）』をVS CodeのClineに投入する。
2. Clineが `scripts/` 配下に「多重挿入防止（冪等性）」を備えた処理スクリプト（例: `scripts/update_features.py`）を1ファイル作成する。
3. Clineがターミナルで `python3 scripts/update_features.py` を実行する。
4. Clineが `git diff` および `git status` で差分を検証し、意図通りの変更が行われたことを確認して完了する。
5. **自律クリーンアップとアーカイブ退避の実行**:
   - 差分検証がPASSした後、Clineはターミナルで直ちに `python3 scripts/cleanup_audit.py --apply` を実行する。
   - 今回作成・実行した一括処理スクリプト（`scripts/update_XXXX.py` 等）が安全に `scripts/archive/` へ自動退避され、作業空間がクリーンな状態に復帰したことを確認して完了とする。

## **🔄 第6章：Phase D - ログ解析とリカバリー・ループ (Feedback Loop)**

実行エラーや意図しない差分が生じた場合、司令塔へログをフィードバックして迅速に解決します。

### **🛠️ 手順**
1. Clineが出力したエラーログや差分サマリーをコピーする。
2. 司令塔（Web版 Gemini）に対し、以下のテンプレートを用いて解析を依頼する。

```text
【ログ解析と次なる一手依頼】
Clineの実行結果ログです。現状の分析を行い、日本学術会議2025年版規格およびガイドラインに準拠したリカバリー指示（Cline向け指示書）を策定してください。
【実行ログ】：[ログの内容をペースト]
```

3. 提示された指示書をClineへ再投入し、問題を確実に解消する。

## **🔍 第7章：Phase E - 改修完了後の三位一体ドキュメント監査 (Triad Review)**

アプリの実装・動作検証が完了した時点で、司令塔は作業を終了せず、直ちに以下の3点について運用の齟齬や追従すべき新ルールがないかを自律的に点検し、改変の要否をユーザーに提示する。

1. **ガイドライン（`docs/guideline.md`）**: 新たなUI設計、CSS規則、データ構造の反映漏れがないか。
2. **開発ワークフロー（`docs/workflow.md`）**: 実装プロセスや検証手順に変更や追記事項がないか。
3. **カスタム指示書（`docs/instruction.md`）**: 司令塔自身の行動指針や出力プロンプト仕様に更新が必要か。

## **⚙️ 【必須セットアップ】プロジェクトルート構成定義**

本フローを正常稼働させるため、以下の構成ファイルをルート直下に配置します。

### **.clinerules (AI全般への絶対遵守事項定義)**
- **0. モード別行動規範とトークン枯渇防止SOP**: Actモードによる確実かつ最小限の差分適用。複数アプリ一括改修時はPythonスクリプト駆動型一括更新を必須とし、AIによる直接多重編集を物理的に禁止。
- **1. 破壊なき進化 (Zero-Modification)**: 既存のHTML構造、CSS、D3.js描画ロジック、計算アルゴリズムは指定がない限り1文字も変更しない。
- **2. ガイドラインの絶対的優先**: `docs/guideline.md` を唯一の正解基準として完全遵守。
- **3. 用語規格の死守**: 日本学術会議（2025年版）に基づく用語の厳格な区別（顕性・潜性、血しょう、かく乱、胚のう、突然変異/変異等）。
- **4. UI/UXバリデーション規格 (v34.4準拠)**:
  - グローバル・ドロワーのブレイクポイント（1024px以下画面外隠蔽・ヘッダートグル、1025px以上ホバー・ピン留め展開）の死守。
  - サイドバーナビ要素（`.nav-item`, `.sidebar-action-btn`）の全幅ブロック状ハイライト（`display: flex; width: 100%; box-sizing: border-box;`）の維持。
  - タッチターゲット最小寸法（44px / モバイル48px）の確保。
- **5. トークン極限圧縮・コンテキスト保護防壁**:
  - 100行を超えるファイル全体の `read_file` を原則禁止。行指定（Offset/Limit）または骨格化テキストを参照すること。
  - 修正適用時は変更箇所の差分（Diff）のみを生成・適用すること。
  - エラーログや巨大データは前処理・切り詰めを行ってからコンテキストに投入すること。
